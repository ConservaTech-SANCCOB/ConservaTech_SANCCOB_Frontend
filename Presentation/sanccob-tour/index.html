    SANCCOB Volunteer Management System

    A mobile app for volunteers and trainers, a web dashboard for coordinators, and one secure API behind both. Built by ConservaTech for the Southern African Foundation for the Conservation of Coastal Birds (SANCCOB), which rehabilitates injured and oiled seabirds, especially African penguins.

    This page is both our presentation and our README. The Tour walks through the same material as short clips. Module: INSY7315 Work Integrated Learning, The Independent Institute of Education. Team of five.

      What we built

      Volunteers

      • Activate an account from an emailed code, then sign in
      • Reset a forgotten password by email
      • Share availability on a Monday to Sunday grid
      • See upcoming shifts and ask to change or cancel one
      • Track hours worked and training progress
      • Edit their own profile

      Coordinators (admins)

      • Dashboard with today's shifts, new volunteers by age, shift split and conservation numbers
      • Create volunteers, which sends the activation email
      • Schedule shifts, generate a weekly roster and publish it
      • Approve or decline change requests, and see open vacancies
      • Reports and staff training progress

      Trainers

      • Unlock the trainer screens with the staff PIN on a shared device
      • Choose their own name from the trainer list
      • Sign off a volunteer's skill

      Rules the system enforces

      • A volunteer must be signed off on every skill a shift needs
      • No more than 40 hours a week, 5 days a week or 4 days in a row
      • Supporting areas must be completed before pen routines
      • An approved cancellation makes the shift vacant again, and the history is kept
      • Pen shifts are staffed at one volunteer per 30 birds

      Architecture

      Two clients talk to one API. The API is the only thing that touches the database, so every rule and every permission check lives in one place.

      • Layered API. Controllers handle HTTP and authorization, services hold the business rules, repositories and Entity Framework Core handle data.
      • Repository pattern. Core entities such as users, volunteers and change requests sit behind interfaces, so services can be tested on their own.
      • Dependency injection. Every service and repository is registered once and injected where it is needed.
      • DTOs. The API returns purpose-built shapes and never exposes database entities directly.

      Security

      ThreatHow we handle it
      Stolen or reused tokenSigned JWTs with an expiry. Logging out revokes the token id on the server, and every request checks it.
      Weak or leaked passwordsPasswords are hashed with ASP.NET's password hasher and must meet complexity rules. Activation codes expire after 48 hours and reset codes after 1 hour.
      Finding out who has an accountThe forgot-password endpoint gives the same answer whether or not the email exists.
      Acting as someone elseVolunteer identity is read from the token, never from the request body. Trainer identity comes from a signed claim set when a trainer picks their name.
      Access to the wrong dataRole-based authorization on endpoints, with admin-only writes.
      InjectionEntity Framework Core parameterises every query. Times, days and age brackets are checked against fixed lists.
      Cross-site scriptingBoth front ends are React, which escapes rendered values by default, and the API returns JSON only.
      Cross-origin abuseCORS allows only the dashboard origin and local development.
      Guessing the trainer PINThe PIN endpoint is rate limited.
      Exposed secrets and trafficKeys and connection strings live in Azure settings and user secrets, not in source control. Everything is served over HTTPS, and the database connection uses TLS.

      DevOps

      Every change goes through a pull request. Tests run automatically, and deployment only happens after they pass.

      • Branching. Feature branches merge to main through pull requests.
      • Automated tests. The xUnit project runs on every push and pull request, using an in-memory database for service tests.
      • Gated deployment. The deploy job needs the test job to pass and only runs on a push to main.
      • Mobile. Each build profile has its own update channel, so a JavaScript or UI fix reaches installed apps without a new build.

      API

      Add these keys to your user secrets (in Visual Studio, right-click the project and choose Manage User Secrets), then run it from the solution folder.

      {
  "ConnectionStrings": { "DefaultConnection": "<Neon connection string>" },
  "Jwt": { "Key": "<long random string>", "Issuer": "<issuer>", "Audience": "<audience>" },
  "Acs": { "ConnectionString": "<Azure Communication Services>", "SenderAddress": "<sender email>" },
  "TrainerAccess": { "Pin": "<6 digits>" }
}
      dotnet run     # start the API
dotnet test    # run the xUnit tests

      On Azure, the same keys are application settings, with a double underscore in place of the colon (for example Jwt__Key).

      Choices and limits

      • Trainer access. A shared staff PIN unlocks the trainer screens, then each trainer picks their name. It suits a shared device with no confidential data, and sign-offs still carry a verified trainer id.
      • Availability. Volunteers resubmit availability each week instead of keeping a permanent pattern.
      • Conservation numbers. These are entered by an admin, not calculated from bird records.
      • Hosting. Free tiers on Azure and Neon are fine for a demonstration. Real use needs paid tiers.
      • Distribution. iOS testers use TestFlight and Android testers use an APK. Public store release would need an organization developer account and store review.
      • Sessions. There is no token refresh yet, so users sign in again when a token expires.
      • Testing. Automated tests across the stack: backend xUnit, mobile Jest/RTL (120 passing), web app Jest (50 passing across 14 suites).
      • Privacy. The system holds personal information, so production use would need a POPIA review.
